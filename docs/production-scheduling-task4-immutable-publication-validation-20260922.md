# Task 4：不可变排程版本和发布流程验收报告

日期：2026-09-22
范围：本地代码、生产只读副本的独立副本
生产环境：未修改

## 1. 本阶段目标

将“生成排程”与“正式生产执行排程”分开：

1. 新生成和人工调整得到的是候选草稿版本；
2. 草稿内容形成规范化 SHA-256 内容摘要；
3. 草稿必须提交并由独立审批人批准；
4. 发布必须填写原因和幂等键；
5. 只有发布事务可以切换订单正式排程版本；
6. 发布后版本、条目和工作流事件不可篡改；
7. 再次生成草稿不得清除或替换已有正式投影；
8. 发布失败时数据库事务整体回滚。

## 2. 实现内容

### 2.1 V092 数据库迁移

新增迁移 `V092 - Freeze and audit schedule revision publication`：

- `schedule_revisions.content_digest`：不可变条目集合的规范化摘要；
- `publication_reason`：发布原因；
- `publication_idempotency_key`：发布幂等键；
- `schedule_node_workflow_events` 支持 `publish` 事件；
- 同一订单最多一个 `published` 版本；
- 已批准、已发布、已取代和已取消版本受到数据库触发器保护；
- 当前版本指针只能指向本订单、已批准且已发布的版本；
- 禁止直接清空正式版本指针；
- 发布事件继续保持不可更新、不可删除。

### 2.2 内容完整性

新增统一完整性检查：

- 条目集合必须与订单工序集合完全一致；
- 每条 `payload_json` 必须与 `payload_digest` 一致；
- 订单、订单工序、工序、路线版本和工序版本快照必须一致；
- 版本 `content_digest` 必须与全部条目的规范化摘要一致；
- 提交、批准和发布前均执行完整性校验。

### 2.3 草稿与正式投影隔离

- 已存在正式版本时，新草稿直接写入不可变版本条目；
- 草稿生成不会删除或覆盖 `order_process_schedules` 正式投影；
- 查询界面展示最新候选草稿，但正式容量和生产执行投影保持不变；
- 发布事务根据已批准的不可变条目重建正式投影；
- 发布成功后才更新 `orders.current_schedule_revision_id`、计划日期和重排标记；
- 原正式版本自动变为 `superseded`。

### 2.4 受控发布 API 与前端

- `POST /api/schedule/revisions/<id>/publish` 现在强制校验：
  - `reason`；
  - `idempotency_key`；
  - 当前登录操作人。
- 相同幂等键和相同输入安全重放；
- 相同幂等键配合不同输入返回冲突；
- 前端修正生命周期状态与审批状态混用的问题；
- 正确显示“草稿、待审批、已批准待发布、已驳回、已发布、已取代、已取消”；
- 发布与提交、批准、驳回一致，必须填写操作原因。
