## 职责和执行边界

`ScheduleConflictPolicy.detect()` 由 209 行缩为 8 行，只建立快照、依次调用检测器、交给汇总层合并证据。五个检测器集中在独立领域模块中，各自入口最长 22 行；没有把原有长方法整体转移到新文件。

| 组件 | 职责 |
|---|---|
| `schedule_conflict_snapshot.py` | 归一化生产节点/旧产线、上海时间区间，记录有效候选、无效候选、既有占用、不可用时段、工序及历史配对关系 |
| `ConflictDetectionSnapshot` | 复用 `schedule_planning.py` 的递归冻结能力，将映射、列表和集合冻结为只读映射、tuple 和 frozenset；与调用方数据脱离 |
| `CapacityConflictDetector` | 无效内部容量区间、无锁独占容量重叠、外协或非排程工序非法占用内部容量 |
| `LockedTaskConflictDetector` | 涉及锁定任务的独占重叠，保留原有锁定冲突优先分类 |
| `DowntimeConflictDetector` | 候选与同一资源停机/不可用时段的重叠及来源证据 |
| `SerialConflictDetector` | 同一道内部工序内的序列件重复分配，包括已阻断工序的序列分配 |
| `SequenceConflictDetector` | 按既有工序序号及工序 ID 排序，检查相邻未阻断内部工序的前后关系 |
| `schedule_conflict_evidence.py` | 统一关联对象、中文原因、重叠时间和分钟数、锁定标记、details、SHA-256 digest；按 digest 去重并稳定排序 |

五个检测器收到同一个递归冻结快照，无共享可变缓存。每次检测产生独立证据对象，汇总层及调用方修改结果不会污染快照或其他调用。容量和锁定检测复用同一纯配对迭代逻辑，按锁定属性区分；不保留可变迭代进度，也不物化所有候选对。

## 保留的行为

修改生产代码前，从原检测器冻结 `tests/schedule_conflict_behavior_v1.json`。35 个样本的摘要涵盖完整冲突列表、各字段和 evidence digest、输出顺序、汇总、交期风险，以及异常类型和消息。修改后没有重新生成 golden。

- 七类阻断冲突名称、中文原因、关联对象、重叠最小一分钟和 digest 编码保持原样。
- 两个批次区间允许重叠；任一参与者为独占时继续检测。锁定不改变两个批次区间允许重叠的规则。
- 候选和已有占用仍按原遍历方向配对；保留按字典相等关系排除重复候选的历史行为。冻结前保存首个相等候选的位置，避免 list/tuple 冻结后变相改变配对结果。
- 无效候选仍产生冲突；无效已有占用和不可用时段仍忽略。资源 ID 转换和序列节点排序的既有异常继续传播。
- 外协和非排程工序不参与序列和前后工序检查；已阻断内部工序仍检查序列重复，但不参与前后工序检查。
- 前后工序继续采用既有全局稳定排序及相邻比较，不夹带按订单重新分组或新的排程规则。
- 按冲突类型、重叠开始、双方工序 ID、digest 排序，保留摘要的首要原因和交期风险优先级。
- API 返回的证据结构、`summarize()` 和交期风险策略保持兼容；不修改生成、重排、版本、SAVEPOINT、失败审计或 `schedule_runs.result_json`。
