# 岗位管理 V070 生产迁移运行手册

## 1. 适用范围与禁止事项

本手册用于岗位稳定根、不可变岗位版本、岗位工序版本映射及业务事实版本绑定的 V070 发布。所有数据库路径、代码目录、服务名、操作人和批准人都必须在当次变更单中明确填写，脚本不包含生产主机、账号、密码或固定生产路径。

未取得当次生产变更的单独明确授权时，只能执行只读预检和隔离副本演练，不得连接生产主机执行写入、迁移、停服、重启或功能开关切换。

## 2. 变更单必填项

- 目标提交完整 SHA、当前生产提交完整 SHA和批准的回退提交完整 SHA。
- 生产数据库明确绝对路径、部署目录、服务名称和附件保留范围。
- 实际操作人、独立批准人、计划开始/结束时间和变更单号。
- 本次唯一幂等键；重试必须复用，不得为同一变更生成新键。
- 迁移前数据库 SHA-256、文件大小、备份路径、备份 SHA-256和备份可打开验证结果。
- 岗位工序恢复证据使用的迁移前备份、当前副本和人工复核清单；每项人工结论必须记录处理人、批准人、时间与依据。

## 3. 发布门槛

以下门槛必须全部为零：

```json
{
  "invalid_position_status": 0,
  "duplicate_position_name": 0,
  "missing_position_process": 0,
  "duplicate_position_process": 0,
  "active_user_missing_position": 0,
  "overlapping_open_assignment": 0,
  "unresolved_recovery_items": 0,
  "foreign_key_violations": 0
}
```

此外，`PRAGMA integrity_check` 必须为 `ok`，预检连接必须为只读，源数据库预检前后的 SHA-256 与文件大小必须一致。

## 4. 备份证据和岗位工序恢复

1. 在不停服阶段先制作可读取的一致性数据库备份，记录源文件和备份文件的 SHA-256及大小。
2. 使用 SQLite 只读方式打开备份，执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`。
3. 对怀疑丢失的岗位工序映射，使用两个明确传入的数据库文件生成证据：

   ```bash
   python scripts/recover_position_processes.py \
     --before-db <迁移前证据数据库> \
     --current-db <当前数据库副本> \
     --output-dir <本次证据目录>
   ```

4. 工具仅在岗位 ID 与身份字段一致、全部工序 ID 与身份字段一致、且当前岗位没有冲突映射时生成 `auto_restored`。工具不会写数据库。
5. `POSITION_PROCESS_EVIDENCE_CONFLICT`、`POSITION_PROCESS_EVIDENCE_MISSING`、岗位身份冲突或目标岗位缺失均必须人工复核。不得按名称相似度、序号邻近或推测自动恢复。
6. 人工项完成独立复核后，在清单中记录 `resolution_status=resolved` 或 `accepted`；保留原始 CSV，不覆盖原证据，生成带新 SHA-256 的批准版 manifest。

## 5. 生产只读预检

在生产数据库明确路径上运行：

```bash
python scripts/preflight_position_v070.py \
  --db <生产数据库绝对路径> \
  --recovery-manifest <批准版恢复-manifest.json> \
  --output <证据目录/position-v070-preflight.json>
```

仅当退出码为 0、`ready=true`、所有门槛为零、`source_unchanged=true` 时进入副本演练。任何未解决人工项、完整性问题、重复岗位名称或异常引用都应停止发布。

## 6. 隔离副本演练

副本目标必须不存在且不得指向源数据库：

```bash
python scripts/validate_position_v070_replica.py \
  --source-db <生产数据库绝对路径> \
  --replica-db <一次性演练副本路径> \
  --recovery-manifest <批准版恢复-manifest.json> \
  --evidence <证据目录/position-v070-replica-validation.json> \
  --apply \
  --confirm-replica-validation
```

验收报告必须满足：

- `status=passed`、`source_unchanged=true`、`blocking_failures=[]`。
- 数据库版本达到 V070 或当前更高的已审核版本，完整性为 `ok`，外键异常为零。
- 岗位、岗位工序、员工、报工、绩效来源事实、评分修订版和岗位目标的迁移前字段快照不变。
- 仅按批准 manifest 恢复岗位工序；恢复外的受保护记录不得变化。
- Legacy 岗位与 V1 当前投影的名称、描述、状态、稳定编码及工序集合完全一致。
- 07:00 生产口径的历史绩效分配快照保持不变；仅合格的开放分配在切换点关闭并生成绑定 V1 的新分配。
- V070 直接重放两次后逻辑快照不变。
- 证据 JSON 与所有输入、输出数据库的 SHA-256 已归档。

## 7. 正式迁移顺序

1. 再次核对目标提交、生产数据库 SHA-256、操作人、独立批准人和幂等键与变更单完全一致。
2. 部署已审核代码但保持四个岗位版本化开关为 `false`。
3. 创建停服前最终备份，验证可打开、完整性、外键、SHA-256和文件大小；备份不得放在会被代码部署覆盖的目录。
4. 停止写入流量并确认应用进程已退出；记录停服时间。
5. 对批准 manifest 中有精确证据的映射执行受控恢复；恢复条数和集合必须与副本演练一致。
6. 执行数据库迁移，确认 `PRAGMA user_version`、完整性、外键、V070 manifest 计数与副本演练一致。
7. 启动服务，先保持 Legacy 查询和写入路径，完成健康检查后按四阶段切换功能开关。

## 8. 四阶段功能开关

功能开关只能按以下顺序形成连续前缀，不得跳级：

1. 查询与兼容审计：`POSITION_VERSIONED_QUERY_ENABLED=true`，同时 `POSITION_COMPAT_AUDIT_ENABLED=true`。
2. 版本化写入：`POSITION_VERSIONED_WRITE_ENABLED=true`。
3. Legacy 写入阻断：`POSITION_LEGACY_WRITE_BLOCKED=true`。
4. 稳定观察期结束后，兼容审计的关闭必须另行审批；其余三个开关保持开启。

每一阶段都要重载或重启服务，并完成健康、权限、查询差异和写入行为验收后才能进入下一阶段。开关组合校验失败应保持服务失败关闭，不得临时绕过。

## 9. 生产验收

- 健康接口正常、数据库连接正常、服务日志无迁移异常、外键异常或敏感数据明文。
- 查看者只能查看岗位当前版、待审版、历史版和影响摘要，不能创建、提交、批准或退休。
- 制单人可创建修订并提交，不能批准自己的修订；独立批准人可批准或驳回，重复命令按同一幂等键返回同一结果。
- Legacy 查询与版本化当前投影一致；Legacy 写入在最终阶段稳定返回 HTTP 409 和约定错误码。
- 新报工绑定精确 `submit_position_version_id`，新绩效来源事实、岗位目标和评分修订版绑定精确岗位版本。
- 历史 NULL 版本事实仍显示保存的岗位名称快照，不被当前岗位改名覆盖。
- 已退休岗位不能授权新业务；历史在制事实仍可按原岗位版本查询、导出和追溯。
- 桌面与移动端岗位四视图无横向溢出、遮挡或不可操作按钮。

## 10. 回滚边界

功能开关阶段失败时，先按逆序关闭本次新开启的开关并恢复到最后一个已验收阶段。代码问题但数据库 V070 已成功且数据验收通过时，只能回退到明确支持 V070 的批准提交，不得用旧二进制直接读取新结构。

迁移执行中断、完整性失败、外键异常、受保护快照变化、Legacy/V1 差异或错误恢复映射出现时：保持停服，保存失败现场数据库和日志，恢复停服前最终备份，再切换到批准的回退提交。附件目录不随数据库回滚删除或覆盖。回滚后重新验证数据库 SHA-256、完整性、服务健康和关键历史查询，并将失败证据与回滚证据一并归档。

已经产生真实版本化业务写入后，不允许通过删除版本、事件或事实绑定来“回滚”。此时必须停止新增写入，按受控修订或前滚迁移处置，并重新取得业务和技术批准。
