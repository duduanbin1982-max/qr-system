# 库存管理双视图与受控跨订单出库设计

日期：2026-09-28

状态：业务设计已确认

适用系统：生产管理系统库存管理模块

## 1. 背景

现有库存列表以库存记录和订单来源为主，能够完成入库、出库、调整、流水、预留、批次、库位、盘点和低库存管理，但缺少按同一产品统一查看库存的业务入口。用户需要在不丢失订单、批次、序列号、质量和成本追溯的前提下，使用两种方式查看库存：

1. 按订单查看；
2. 按同一产品编码查看。

本设计采用“库存事实按订单保留、产品编码视图实时聚合、跨订单出库受控分配”的架构。产品聚合不是新的库存事实，不允许仅修改聚合总量而不记录实际扣减来源。

## 2. 目标

- 在同一库存工作台中提供“按订单”和“按产品编码”两种视图。
- 以稳定的 `product_id` 识别产品，当前编码和历史编码别名均可查询到同一产品。
- 产品视图实时汇总库存、预留、冻结、可用量、订单数、批次数和库位数。
- 同一产品的不同规格、路线版本、质量状态和批次限制分层展示，禁止错误混用。
- 产品视图出库默认使用 FIFO，也允许具备权限的用户指定订单、批次、库位或库存记录。
- 所有正式扣减必须落到具体库存记录，并保存完整分配明细、幂等证据和审计事件。
- 保持现有按订单库存、库存流水、预留、批次和序列号行为兼容。

## 3. 非目标

- 本阶段不建立脱离订单来源的物理共享库存池。
- 不删除、合并或重写历史库存记录和库存流水。
- 不用产品名称、相似型号或模糊匹配自动认定产品身份。
- 不在无法唯一解析产品身份时猜测归组。
- 不允许产品聚合行直接成为可扣减库存实体。
- 本设计不授权代码合并、数据库迁移或生产部署。

## 4. 已确认的业务决策

1. 产品编码视图采用受控共享模式：库存事实仍保留订单来源。
2. 产品归组以 `products.id` 为稳定身份，`products.product_code` 是当前展示编码，`product_code_aliases` 用于识别历史编码。
3. 出库采用混合模式：默认 FIFO，可切换为指定订单或批次。
4. 同一产品允许查看总库存，但必须按规格、路线版本、质量状态和批次兼容性分层。
5. 低库存采用订单级和产品级双层预警。
6. 两种视图共享权限体系，导出内容受当前数据权限限制。
7. 首期使用实时聚合查询，并预留后续增加汇总投影表的能力。
8. UI 采用“双视图切换 + 产品编码分组工作台 + 右侧详情与出库抽屉”。

## 5. 总体架构

### 5.1 库存事实层

库存事实继续以具体库存记录为核心，保留订单、产品、批次、库位、序列号、质量状态、数量、预留、冻结及库存流水。跨订单出库只是一种来源选择方式，不改变事实存储粒度。

### 5.2 产品聚合查询层

新增只读的产品库存查询能力，按 `product_id` 实时聚合用户有权限查看的库存事实，生成产品汇总、兼容分组和明细树。聚合层不写库存。

### 5.3 来源分配层

新增纯业务分配器，根据申请数量、兼容分组、FIFO 顺序和人工限制，返回具体库存来源及数量。分配器不访问数据库、不提交事务。

### 5.4 正式出库应用层

正式出库应用服务负责权限、幂等、并发复核、来源分配、库存扣减、流水、分配明细和审计。以上操作必须处于单一数据库事务中。

## 6. 产品身份与数据模型

### 6.1 产品身份

- `product_id`：聚合和业务判断的稳定主键；
- `products.product_code`：当前产品编码；
- `product_code_aliases`：历史产品编码；
- 订单和库存中的编码、名称字段：历史快照，不作为唯一产品身份。

### 6.2 库存身份解析顺序

历史库存按以下顺序解析产品：

1. 库存记录已有 `product_id`；
2. 关联订单已有 `product_id`；
3. 订单产品编码唯一匹配当前产品；
4. 订单产品编码唯一匹配历史编码别名；
5. 无法唯一匹配时标记为“产品身份待确认”。

不得使用产品名称或相似型号进行自动归组。

### 6.3 建议新增或补齐的字段和表

在实际实施前先核实现有迁移，已存在的结构直接复用。目标能力包括：

- `inventory.product_id`；
- `inventory.product_code_snapshot`；
- `inventory.product_name_snapshot`；
- 入库时路线版本、工序版本等来源快照（现有来源表能够可靠提供时可通过关联读取）；
- `product_inventory_thresholds`：产品级安全库存配置；
- `inventory_allocation_runs`：分配请求、幂等键、模式、摘要、状态和操作人；
- `inventory_allocation_items`：具体库存来源及分配数量。

正式表名可依照仓库现有命名规范调整，但职责不得合并回聚合查询接口。

### 6.4 兼容分组

产品总览下按以下维度形成兼容分组：

- `product_id`；
- 型号和规格；
- 路线版本；
- 质量状态；
- 批次限制；
- 其他已配置的出库兼容属性。

库位是明细和分配维度，不改变产品身份。不同库位可在规则允许时共同满足同一申请，但必须分别记录扣减明细。

### 6.5 数量口径

统一定义：

```text
可用库存 = 现存数量 - 已预留数量 - 冻结数量
```

产品汇总从明细逐条求和，返回总数量、总预留、总冻结、总可用、订单数、批次数和库位数。不得使用独立维护但不可对账的总量字段作为首期事实来源。

## 7. API、服务和仓储职责

### 7.1 API

保留现有按订单库存接口，并新增：

```text
GET  /api/inventory/product-groups
GET  /api/inventory/product-groups/{product_id}/details
POST /api/inventory/product-groups/{product_id}/allocation-preview
POST /api/inventory/product-groups/{product_id}/outbound
```

- 产品汇总和详情接口返回稳定、独立的响应结构；
- 不让原 `/api/inventory` 因查询参数不同而返回两套不兼容结构；
- 所有列表接口必须支持服务端分页、排序和受控筛选上限。

### 7.2 `ProductInventoryQueryService`

负责产品身份解析、权限范围内聚合、兼容分组、双层预警和身份异常标记。该服务只读，不扣减库存。

### 7.3 `InventorySourceAllocator`

这是不访问数据库的纯分配器。输入包括产品身份、申请数量、FIFO 或人工模式、兼容分组、允许的订单/批次/库位限制和候选库存；输出包括：

```text
inventory_id
order_id
batch_id
location
allocated_quantity
allocation_reason
```

### 7.4 正式出库应用服务

执行顺序：

1. 校验权限和请求；
2. 校验幂等键及请求摘要；
3. 在事务中重新读取候选库存并建立并发保护；
4. 重新计算或验证来源分配；
5. 校验分配总量等于申请量；
6. 扣减具体库存并更新预留；
7. 写库存流水、分配运行、分配明细和审计事件；
8. 提交事务并返回结果。

任何一步失败时全部回滚。禁止出现库存已扣减但分配证据未保存的半完成状态。

### 7.5 仓储

仓储提供：

- 按订单读取库存事实；
- 按产品身份读取可聚合库存事实；
- 按具体 `inventory_id` 读取、锁定和扣减；
- 保存分配运行和分配项目；
- 读取安全库存阈值。

复杂 SQL 留在仓储层，业务兼容判断和 FIFO 规则留在领域服务或分配器，Route 不直接执行 SQL。

## 8. UI/UX

### 8.1 工作台结构

```text
库存管理
├── 按订单
└── 按产品编码
    ├── 产品汇总列表
    ├── 兼容分组展开
    └── 右侧详情/出库分配抽屉
```

### 8.2 按订单视图

主要字段：订单号、客户、产品编码、产品名称、订单数量、当前库存、预留、冻结、可用、库位、状态和操作。保留现有用户操作习惯与兼容 API。

### 8.3 按产品编码视图

汇总行显示：

- 当前产品编码和名称；
- 型号、规格摘要；
- 总库存、总预留、总冻结和总可用；
- 涉及订单数、批次数和库位数；
- 产品级预警、订单风险数和身份异常状态。

展开后显示兼容分组，再展开订单、批次、库位和库存明细。

### 8.4 详情与出库抽屉

桌面端使用右侧抽屉，移动端使用全屏页面。抽屉包括：

- 产品与兼容分组信息；
- 申请出库数量；
- FIFO/指定来源切换；
- 来源订单、批次、库位和库存记录；
- 分配数量、分配后余额；
- 冲突、缺口和预警；
- 固定底部的预览、重新分配和确认操作。

改变默认 FIFO 时必须填写原因。正式提交前显示完整分配明细并二次确认。

### 8.5 查询和可用性

两种视图支持关键词、订单、产品、客户、库位、质量状态、预警状态、库存状态、排序、分页和保存筛选。状态必须同时使用文字、图标和颜色表达。空状态、权限不足、身份异常和加载失败均提供明确处理建议。

## 9. 出入库、预留和追溯规则

### 9.1 入库

订单完工入库保存来源订单、产品身份、编码和名称快照、批次、序列号、库位、质量状态、来源版本、数量、操作人和时间。无订单库存必须明确标记为通用库存，不得伪造订单。

### 9.2 FIFO

候选库存必须质量允许、未冻结、可用量大于零且属于选定兼容分组。稳定排序为：

```text
入库时间 → 批次时间/编号 → 库位优先级 → inventory_id
```

### 9.3 人工指定

具备 `inventory:allocate` 权限的用户可指定订单、批次、库位或库存记录，但不能绕过质量、冻结、序列号、预留和兼容分组约束。

### 9.4 预览和正式提交

预览不修改库存。正式提交必须重新读取库存；若库存版本或可用量变化，预览失效并返回明确冲突，要求重新确认。

默认不静默部分出库。库存不足时返回缺口数量。序列号库存必须落实到具体序列号。

### 9.5 预留

产品视图可汇总显示预留，但正式预留必须落实为“需求订单—具体库存—预留数量”。解除或转移预留必须有权限、原因和审计事件。

### 9.6 审计与撤销

正式操作保存幂等键、请求摘要、产品和编码快照、分配模式、分配前后数量、来源订单、批次、库位、序列号、人工原因、操作人和时间。已完成流水不得删除或覆盖；撤销通过关联原操作的反向流水完成。

## 10. 权限、错误、预警和导出

### 10.1 权限

目标权限：

- `inventory:view`；
- `inventory:export`；
- `inventory:inbound`；
- `inventory:outbound`；
- `inventory:allocate`；
- `inventory:reserve`；
- `inventory:adjust`；
- `inventory:audit`；
- `inventory:manage_threshold`。

实施时优先映射现有权限，只有现有权限不能表达业务边界时才新增权限。产品聚合只能基于用户有权查看的明细，禁止因聚合扩大订单、客户或仓库数据范围。

### 10.2 双层预警

订单级阈值和产品级阈值分别配置和计算。产品汇总显示产品状态、风险订单数、总缺口和最早受影响订单。产品总量充足不得掩盖某个订单已被预留或不可使用的事实。

### 10.3 错误处理

返回明确业务错误，包括产品身份冲突、无兼容库存、库存缺口、并发占用、批次或质量禁止、预览过期、数据权限不足和幂等冲突。未知异常返回统一错误编号并在服务端保留关联日志，不向用户只显示无法处理的“服务器内部错误”。

### 10.4 导出

按订单视图导出订单明细；按产品编码视图支持“仅汇总”或“汇总及展开明细”。导出必须应用与列表相同的数据范围、筛选条件和审计规则。

## 11. 历史迁移与发布

### 11.1 迁移预检

在生产数据库副本生成：

1. 已有明确 `product_id` 的库存；
2. 可由订单补齐的库存；
3. 可由当前编码或历史别名唯一匹配的库存；
4. 无法匹配或冲突、需要业务确认的库存。

唯一匹配才允许自动补齐。迁移前后库存、预留和订单库存必须守恒，原始流水不得改写。

### 11.2 功能开关与阶段

建议独立控制：

- 产品聚合查询；
- 产品双视图 UI；
- 来源分配预览；
- 正式跨订单出库；
- 产品级安全库存。

发布顺序：

1. 只读观察；
2. 开放双视图、预警和导出；
3. 开放分配预览；
4. 验证通过后开放正式受控出库。

### 11.3 回退

任何生产发布必须在单独授权的维护窗口执行。失败时恢复部署前数据库和前端备份、回退代码，并保留 `data/`、附件、迁移日志、分配证据和审计记录。只读阶段产生的异常清单不得作为库存事实写回生产。

## 13. 最终验收标准

- 库存、预留、冻结和可用量守恒；
- 每个产品汇总数均可追溯到具体订单和库存记录；
- 无法识别产品的库存不会被错误归组；
- 历史编码能通过别名归入正确产品；
- 不同兼容分组不能错误混用；
- FIFO 和人工指定均输出、保存明确来源；
- 正式出库不存在重复扣减、超扣或负库存；
- 事务失败不留下半完成库存、流水或证据；
- 双层低库存预警准确；
- 聚合后数据权限不扩大；
- 旧按订单库存及原有出入库流程回归通过；
- 正式操作均具备操作人、原因、幂等键和不可删除的审计证据；
- 发布失败可按授权参数恢复数据库、前端和代码。
