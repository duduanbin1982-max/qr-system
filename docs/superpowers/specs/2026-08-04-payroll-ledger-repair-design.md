# 工资核算版本化台账修复设计

## 状态

- 设计日期：2026-08-04
- 状态：已确认
- 适用范围：工价版本、计件工资、返工工资、工资调整、工资批次、历史修订、权限与工资导出
- 目标版本：数据库迁移 55 及后续工资台账发布

## 背景与生产证据

现有工资模块直接以报工记录和当前 `route_prices` 计算工资，并以 `wage_snapshots` 保存按员工汇总的 JSON 快照。审计确认以下问题已经影响生产数据：

- 2026-07 已确认快照保存工资 98,991.20 元，其中包含 196 条 8 月明细、金额 8,421.30 元；按快照自身 7 月明细合计为 90,569.90 元。
- 3,171 条已审批正常报工中有 1,831 条无法匹配工资查询使用的工价。
- 1,727 条是因为当前工价生效日晚于报工时间，其中 1,385 条对应的路线工序已有工价变更历史。
- 102 条没有对应路线工序工价，2 条订单没有工序路线。
- 63 份历史快照中有 26 份曾在锁定后重新保存。
- 工资保存和锁定接口错误地使用 `wages:view`，生产存在两个只有工资查看权限、没有工资编辑权限的非管理员角色。
- 历史非在职员工已有已审批报工被当前“仅查询在职工人”的逻辑排除。
- 月初 00:00 至 06:59 的报工与生产日报采用不同月份口径。

本设计采用版本化工资台账。报工、工价和调整项是工资计算输入，工资批次及其明细才是正式结算结果。已锁定和已确认结果不可原地修改，修正只能创建新版本。

## 已确认业务决策

1. 工资月份统一采用生产统计日边界：每日 07:00 至次日 07:00；月初 00:00 至 06:59 归上月最后一个生产日。
2. 审计发现的 1,727 条历史报工全部按迁移时的当前工价结算，作为一次性历史迁移政策。
3. 其余 104 条记录进入工资异常队列，补齐路线或人工指定工价并审批前不得结算，不得静默按零元处理。
4. 2026-07 原确认快照保留为旧版本，新建修订版 V2；禁止直接覆盖旧版。
5. 工资制单和审批采用双人复核，同一批次制单人与审批人不得相同。
6. 奖金、补贴、扣款进入正式工资快照；锁定后只能通过修订版调整。
7. 同一员工同月允许多笔同类型调整，每笔必须有独立原因、制单人和时间。
8. 返工工资采用路线工序级倍率，默认 0；历史返工缺少明确倍率时进入异常队列。
9. 选择“版本化工资台账”方案，不建设个税、社保、银行付款或完整财务总账。

## 目标

1. 工资金额可从正式批次追溯到每条报工、工价版本、返工倍率和调整项。
2. 工价变化不改变已经生成或确认的历史工资。
3. 工资月、日报和报工统计使用同一 07:00 边界。
4. 缺少计价依据时明确阻断结算，不生成静默零工资。
5. 锁定和确认结果由服务层与数据库共同保护。
6. 历史修订保留原版本、修订版本、差额和审批链。
7. 员工只能查看本人正式工资，工资经办人与审批人按职责授权。
8. 金额使用定点整数计算，消除 `REAL/float` 精度漂移。

## 非目标

- 不实现考勤工资、固定工资、加班工资、个税、社保和公积金。
- 不实现银行代发、付款核销或会计凭证。
- 不自动决定 104 条异常记录的工价。
- 不删除或改写原 `wage_snapshots` 历史记录。
- 不把系统管理员视为默认工资审批人，也不允许管理员隐式绕过双人复核。

## 总体架构

工资核算拆为四个边界清晰的组件：

1. `PriceVersionService`：维护带生效区间的正常工价与返工倍率。
2. `PayrollCalculationService`：在一致性读视图中把报工和调整项计算为工资明细。
3. `PayrollWorkflowService`：管理草稿、异常、复核、锁定、确认、作废和修订状态。
4. `PayrollRepository`：集中访问工资台账表，执行幂等、并发和不可变约束。

工资查询、导出和工资条只读取工资台账。实时计算结果只能标记为“预估”，不能冒充正式工资。

## 生产月边界

所有工资入口复用 `modules.domain.reporting_day` 的统一边界函数。给定 `YYYY-MM`：

```text
period_start = 当月1日 07:00:00
period_end   = 次月1日 07:00:00
范围规则     = created_at >= period_start AND created_at < period_end
```

禁止在工资仓储中继续使用 `DATE(created_at)`、`23:59:59` 或自然月 `start of month` 计算正式工资。

## 数据模型

### 工价版本 `route_price_versions`

字段至少包括：

- `id`
- `route_id`
- `process_id`
- `normal_unit_price_micros`：正常工价，单位为万分之一元
- `rework_rate_basis_points`：返工倍率，0 至 10,000，10,000 表示 100%
- `valid_from`
- `valid_to`：空值表示持续有效
- `status`：`draft`、`approved`、`retired`
- `created_by`、`created_at`
- `approved_by`、`approved_at`
- `remark`

约束：

- 同一路线工序的已批准版本生效区间不得重叠。
- 新工价必须新增版本，不允许原地覆盖已批准版本。
- 工价版本一旦被工资明细引用，不得删除或修改金额与生效区间。
- 原 `route_prices` 在迁移期只作为当前工价来源和兼容视图，不再作为正式工资计算依据。

### 工资批次 `payroll_batches`

字段至少包括：

- `id`
- `payroll_month`
- `version`
- `period_start`、`period_end`
- `status`
- `source_cutoff_at`
- `normal_wage_cents`
- `rework_wage_cents`
- `bonus_cents`、`allowance_cents`、`deduction_cents`
- `payable_wage_cents`
- `prepared_by`、`prepared_at`
- `submitted_at`
- `locked_by`、`locked_at`
- `confirmed_by`、`confirmed_at`
- `voided_by`、`voided_at`、`void_reason`
- `supersedes_batch_id`、`superseded_by_batch_id`
- `revision_reason`
- `row_version`

约束：

- `(payroll_month, version)` 唯一。
- 同一月份最多一个未被替代的已确认版本。
- `prepared_by` 不得等于 `locked_by` 或 `confirmed_by`。
- 锁定后工资明细和金额字段不可更新。
- 作废批次不可恢复，只能创建新版本。

### 员工工资行 `payroll_employee_lines`

每个批次、员工一行，字段至少包括：

- `batch_id`、`employee_id`
- `employee_name_snapshot`
- `employee_no_snapshot`
- `position_name_snapshot`
- `normal_quantity`
- `rework_quantity`
- `normal_wage_cents`
- `rework_wage_cents`
- `bonus_cents`、`allowance_cents`、`deduction_cents`
- `payable_wage_cents`
- `exception_count`

员工离职、改名、换岗位或工号变化不得改变历史工资行。

### 工资明细 `payroll_detail_lines`

每条报工或调整项对应一条不可变工资明细，字段至少包括：

- `batch_id`、`employee_line_id`
- `source_type`：`normal_work`、`rework_work`、`bonus`、`allowance`、`deduction`
- `source_id`
- `work_record_id`
- 报工时间、订单号、产品、路线、工序等业务快照
- `quantity`
- `price_version_id`
- `unit_price_micros`
- `rework_rate_basis_points`
- `amount_cents`
- `resolution_method`：`versioned_price`、`current_price_migration`、`manual_exception_resolution`
- `resolution_reason`
- `resolved_by`、`resolved_at`

同一批次中，同一报工或调整项只能出现一次。工资查询不得在读取明细时重新关联当前产品、员工、路线或工价覆盖快照语义。

### 工资异常 `payroll_exceptions`

字段至少包括：

- `batch_id`
- `work_record_id`
- `exception_type`：`missing_route`、`missing_price`、`overlapping_price`、`missing_rework_rate`、`invalid_amount`
- 原始业务快照
- `status`：`pending`、`proposed`、`approved`、`rejected`
- `proposed_price_micros`、`proposed_rework_rate_basis_points`
- `proposed_by`、`proposed_at`
- `approved_by`、`approved_at`
- `resolution_reason`

制单人提出处理方案，审批人批准；两者不得相同。未批准异常不生成正式工资明细。

### 工资调整

工资调整改为不可变记录，金额按分存储：

- 类型仅允许 `bonus`、`allowance`、`deduction`。
- 金额必须为正整数分，方向由类型决定。
- 同一员工同月允许多笔同类型记录。
- 每笔记录包含原因、制单人和创建时间。
- 修改通过新增冲销记录和替代记录完成，不执行物理删除。
- 调整项被工资批次引用后不得改变；锁定后新增调整需要新建工资修订版。

旧 `wage_adjustments` 当前生产无数据，可以在迁移中转换为新结构，并保留兼容只读视图。

## 金额计算规则

正式计算仅使用整数和十进制定点算法：

```text
正常明细金额 = ROUND_HALF_UP(数量 × 正常工价万分之一元 ÷ 100) 分
返工明细金额 = ROUND_HALF_UP(数量 × 正常工价 × 返工倍率 ÷ 10,000 ÷ 100) 分
员工实发工资 = 正常工资 + 返工工资 + 奖金 + 补贴 - 扣款
批次合计     = 员工工资行金额的精确整数求和
```

每条工资明细先舍入到分，员工和批次汇总只做整数相加。API 返回整数分和格式化后的元金额，内部不得以二进制浮点数作为正式金额来源。

## 批次生成流程

1. 根据工资月计算 07:00 生产月范围。
2. 在同一数据库事务和一致性读视图中读取已审批正常报工、已审批返工和有效调整项；不按员工当前在职状态或当前角色排除历史报工。
3. 为每条报工匹配报工时点有效的已批准工价版本。
4. 无法唯一匹配时创建工资异常，不生成零金额工资明细。
5. 固化员工、订单、产品、路线、工序、工价和调整项快照。
6. 逐条计算整数分金额，再生成员工工资行和批次合计。
7. 保存 `source_cutoff_at` 和输入摘要，用于检测草稿生成后的数据变化。
8. 返回工资金额、异常数量和输入变化状态。

已审批报工是独立的工资事实。订单后来取消、删除，员工后来离职、改名或调岗，都不能让已审批工资事实从历史批次中静默消失。发现错误时必须创建报工冲销或工资修订版并保留原因和审批记录。

生成接口必须接受幂等键。同一幂等键和相同输入不能重复创建批次或明细。草稿存在且源数据发生变化时，页面显示“数据已变化”，由制单人明确重新生成，不后台静默覆盖。

## 状态机

状态定义：

- `draft`：草稿，可由制单人重新生成。
- `exceptions_pending`：存在待处理异常，不可提交复核。
- `review_pending`：异常已清零，等待审批人复核。
- `locked`：已复核锁定，明细不可修改，可执行最终确认或作废。
- `confirmed`：正式工资版本，可供员工查看和导出。
- `voided`：已作废，只读保留；修正必须新建版本。

允许转换：

```text
draft <-> exceptions_pending
draft/exceptions_pending -> review_pending
review_pending -> locked
locked -> confirmed
locked/confirmed -> voided -> 新建 V2/V3
```

禁止跳过复核直接确认。锁定、确认和作废都必须校验 `row_version`，并发冲突返回 409，不覆盖其他用户操作。

## 权限与数据范围

新增并使用以下权限：

- `wages:view_self`
- `wages:view_all`
- `wages:prepare`
- `wages:approve`

规则：

- 普通员工只能读取自己的预估工资和已确认工资。
- `wages:view_all` 可以读取全员批次、明细、汇总和异常，但不能修改。
- `wages:prepare` 可以生成草稿、提出异常处理、录入调整项和提交复核。
- `wages:approve` 可以批准异常、锁定、确认、作废和批准修订版。
- 同一批次制单人与审批人不得相同。
- 原 `wages:view`、`wages:edit` 和不存在于权限目录的 `prices:view_all` 不再承担新工资流程授权。
- 系统管理员必须显式以审批人身份操作并满足双人规则，`*` 权限不能绕过制单人与审批人分离。

权限迁移必须生成角色影响报告。旧 `wages:view`、`wages:edit` 不自动映射为任何新的敏感工资权限；管理员必须根据职责显式授予 `view_self`、`view_all`、`prepare` 或 `approve`。未完成映射的角色在新模块中默认无权限，以失败关闭方式避免扩大工资数据访问范围。

## 接口设计

新接口按资源和动作划分：

- `GET /api/payroll/me`
- `GET /api/payroll/batches`
- `GET /api/payroll/batches/<id>`
- `GET /api/payroll/batches/<id>/lines`
- `POST /api/payroll/batches`
- `POST /api/payroll/batches/<id>/regenerate`
- `POST /api/payroll/batches/<id>/submit`
- `POST /api/payroll/batches/<id>/lock`
- `POST /api/payroll/batches/<id>/confirm`
- `POST /api/payroll/batches/<id>/void`
- `POST /api/payroll/batches/<id>/revisions`
- `GET /api/payroll/batches/<id>/compare/<other_id>`
- `GET /api/payroll/exceptions`
- `POST /api/payroll/exceptions/<id>/propose`
- `POST /api/payroll/exceptions/<id>/approve`
- `GET/POST /api/payroll/adjustments`
- `POST /api/payroll/adjustments/<id>/reverse`

所有写接口记录审计日志、操作用户、前后状态、业务原因、请求关联 ID 和幂等键。正式导出只读取 `locked` 或 `confirmed` 批次。

旧 `/api/wages*` 接口在过渡期只读，并明确返回 `legacy` 或 `estimate` 标识；完成切换后停止向工资页面提供正式数据。

## 页面设计

工资模块包含：

1. **我的工资**：本人预估工资、正式工资和已确认工资条。
2. **工资批次**：月份、版本、状态、金额、制单人和审批人。
3. **工资明细**：逐条展示报工、工价版本、返工倍率和计算过程。
4. **异常处理**：提出并审批缺路线、缺工价和冲突处理方案。
5. **工资调整**：追加奖金、补贴、扣款和冲销记录。
6. **工价版本**：管理工价、返工倍率和生效区间。
7. **版本对比**：展示员工级和明细级 V1/V2 差额。
8. **审计记录**：查询生成、提交、锁定、确认、作废和导出行为。

草稿统一标记“预估”，不得打印正式工资条。员工只有在批次确认后才能下载正式工资条。页面按钮和路由按权限隐藏，但后端权限仍是唯一安全边界。

CSV 导出统一使用安全单元格格式化，阻断 `=`, `+`, `-`, `@` 开头的公式。工资条和打印页统一进行 HTML 转义，不使用未转义字符串拼接 `document.write`。

## 生产历史迁移

迁移前以生产备份为基线重新统计报工分类。若数量与审计基线 `1,727 + 104 = 1,831` 不一致，迁移停止并生成差异报告，不自行扩大结算范围。

### 工价迁移

1. 将当前 `route_prices` 转换为首个已批准工价版本。
2. 保留原工价历史表只读。
3. 对 1,727 条历史报工创建特殊迁移解析记录，使用迁移切点的当前工价。
4. 每条明细标记 `current_price_migration`，保存政策说明、批次号、当前工价和重算差额。
5. 104 条无法匹配记录生成异常，不自动创建零金额明细。

### 历史工资批次

- 将 2026-06 旧锁定快照导入为只读 Legacy V1，默认不重算。
- 将 2026-07 原确认快照导入为只读 Legacy V1，并标记将被修订版替代；原 `wage_snapshots` 行保持不变。
- 严格按 2026-07-01 07:00 至 2026-08-01 07:00 生成 2026-07 V2。
- V2 输出员工级、明细级和总额差异，完成双人复核后确认并替代 V1。
- 8 月报工只能进入 2026-08 批次，不能出现在 2026-07 V2。

## 异常处理

以下情况必须失败关闭：

| 场景 | 行为 |
| --- | --- |
| 缺少订单路线 | 创建 `missing_route` 异常 |
| 缺少工价版本 | 创建 `missing_price` 异常 |
| 多个工价版本同时有效 | 创建 `overlapping_price` 异常 |
| 返工倍率未明确 | 创建 `missing_rework_rate` 异常 |
| 金额溢出或格式非法 | 创建 `invalid_amount` 异常并回滚 |
| 批次仍有未批准异常 | 禁止提交、锁定和确认 |
| 制单人与审批人相同 | 拒绝锁定、确认和作废 |
| 批次版本冲突 | 返回 409，要求刷新 |
| 锁定或确认后修改 | 拒绝原地修改，要求创建修订版 |

批次生成和状态转换在单一数据库事务中执行，任何失败整体回滚，不留下半批工资。

## 审计与可观测性

必须记录：

- 工价版本创建和批准；
- 工资批次生成和重新生成；
- 异常提出、批准和拒绝；
- 调整项创建和冲销；
- 批次提交、锁定、确认、作废和修订；
- 正式工资导出和工资条下载。

运行指标至少包括：

- 每个工资月的报工数、已计价数和异常数；
- 缺路线、缺工价、工价重叠和缺返工倍率数量；
- 草稿、待复核、锁定和确认批次数；
- 批次重算前后差额；
- 权限拒绝和并发冲突次数。

日志不得输出完整工资明细、会话令牌或敏感环境变量。

## 回滚

- 使用功能开关关闭新工资入口和新写接口。
- 旧工资页面仅恢复只读访问，不允许继续生成或覆盖旧快照。
- 新增工资台账、工价版本、异常和审计数据保留，不删除迁移表。
- 原 `wage_snapshots` 和 `route_prices` 未被改写，可用于历史核查。
- 如果 V2 尚未确认，直接停止影子流程；如果 V2 已确认，按工资状态机作废并记录原因，不执行数据库物理回滚。
- 应用代码回滚不回退向后兼容数据库结构。

## 验收结论

本设计完成后，工资模块的正式金额来源从实时 SQL 汇总切换为版本化工资台账。工价、报工、返工和调整项均以不可变明细参与结算；异常显式阻断，历史修订保留版本，权限和审批满足双人复核。生产历史数据按已确认政策处理，并具备逐条对账和回滚依据。
