# 绩效管理版本化台账修复设计

## 状态

- 设计日期：2026-08-04
- 状态：已确认
- 适用范围：绩效计算、历史修订、岗位目标、主管复核、审批、数据权限、改进计划、历史迁移与查询展示
- 生产基线：提交 `c0817bb15cb6a346de411f94bb8142f04145ad0c`，数据库版本 55

## 背景与审计结论

绩效管理审计未发现 P0，但确认 6 个 P1 和 2 个 P2。在这些问题修复并经过稳定运行前，现有绩效结果不应直接用于奖金、工资调整或解聘决定。

### P1

1. 零产量员工仍可能得到 85 分并显示绿色等级。
2. 绩效按自然月统计，没有使用日报和报工统计统一的每日 07:00 生产统计日边界；已有 5 条报工和 11 条质量评价归属错误月份。
3. `performance_scores` 按员工和月份原地覆盖，已有 64 条生产评分曾被覆盖；同一排名中混入不同计算时间的结果，30 条历史记录缺少稳定岗位快照。
4. 只有全有或全无的 `performance:view`，没有本人、部门和全局数据范围。
5. 产量分以当月同岗位最高产量为基准，37 名员工中 9 名得到产量满分，其中 3 人处于单人岗位组。
6. 主管复核保存和评分重新计算分属两个事务，可能出现复核已保存但评分未更新。

### P2

1. 改进计划没有受控状态机，也没有可验证的复评记录。
2. 报废、返工和质检数据可能从多个来源重复计入质量扣分。

原审计验证中，后端绩效定向测试 51 项通过，前端单元测试 57 项通过，但缺少零产量、07:00 月份边界、评分版本化、范围权限和非法计划状态转换测试。

## 已确认业务决策

1. 采用版本化绩效台账，不在现有覆盖式表结构上打补丁。
2. 现有评分保留为只读 `Legacy V1`；按统一 07:00 口径生成修订版 V2，复核批准后才生效。
3. 产量评分改用按生效月份版本化的岗位目标，不再使用当月最高产量。
4. 无有效产量、入职未满有效样本要求、长期请假或数据样本不足的员工标记为“数据不足”，不评级、不排名、不触发奖惩。
5. 权限拆分为本人、部门、全局查看，以及评分准备、主管复核和独立批准；制单人与批准人必须不同。
6. 主管复核保存、评分重新计算和员工新修订版生成必须位于同一数据库事务。
7. 改进计划采用受控状态机，必须保存执行证据和独立复评结果。
8. 质量事件使用稳定来源标识去重，无法可靠判断的历史记录必须人工确认。
9. 本期绩效结果不自动影响工资；先稳定运行两个完整生产月并对账，再单独评审工资联动。

## 目标

1. 每个合格正式绩效结果均可追溯到生产月份、规则版本、岗位目标、来源事实、主管复核和批准记录；数据不足记录可追溯到明确的资格判定原因。
2. 已批准结果不可原地修改；纠错通过 V3、V4 等新版本完成，旧版本完整保留。
3. 绩效、日报、报工统计和工资统一使用每日 07:00 生产统计日边界。
4. 零产量和数据不足不能被误判为达标，也不能进入排名。
5. 产量得分以稳定岗位目标计算，配置变化不改变历史结果。
6. 主管复核与评分重算具有事务原子性和并发冲突保护。
7. 后端强制执行本人、部门和全局数据范围，前端参数不能扩大权限。
8. 改进计划形成目标、措施、证据、复评和后续处理的可审计闭环。
9. 质量事件不会因多个业务来源而重复扣分。

## 非目标

- 不重写报工、质检、组织架构或工资模块。
- 不改变现有五个评分维度及首版权重。
- 不自动恢复已经被覆盖且无备份的早期评分修订。
- 不根据当前岗位猜测缺失的历史岗位归属。
- 不让绩效自动生成工资调整、奖金、人事处分或解聘动作。
- 不在本期建设完整人力资源、考勤排班或薪酬激励系统。
- 不采用全量事件溯源重建生产、质检和组织域。

## 总体架构

绩效模块拆为五个边界清晰的组件：

1. `PerformanceFactCollector`：按生产月采集报工、质量、人员、岗位、部门和改进计划事实，完成来源归一化与快照固化。
2. `PerformanceScoringEngine`：纯计算组件，只接受事实快照、规则版本、岗位目标版本和复核输入，不直接访问数据库。
3. `PerformanceLedgerService`：创建批次和员工修订版，处理重新计算、提交、退回、批准与版本取代。
4. `PerformanceAuthorizationService`：组合操作权限与数据范围，统一约束查询和命令接口。
5. `PerformanceImprovementService`：管理改进计划状态、证据、复评轮次和状态事件。

现有 `performance_scores` 和 `performance_reviews` 冻结为 Legacy 来源，不再接受新写入。新查询默认返回指定生产月的正式版本：存在已批准 V2 或后续版本时返回最新正式版本，否则回退到 Legacy V1，并明确返回结果来源。

同一生产月份只能有一个当前正式批次。新版本批准时，在同一事务中把旧正式版本标记为已取代，再将新版本设为已批准。任何版本都不物理删除。

## 生产月边界

所有绩效入口复用 `modules.domain.reporting_day`，不得自行拼接自然月条件。给定生产月份 `YYYY-MM`：

```text
period_start = 当月 1 日 07:00:00
period_end   = 次月 1 日 07:00:00
查询范围     = business_at >= period_start AND business_at < period_end
时区         = Asia/Shanghai
```

月初 00:00 至 06:59 归入上月最后一个生产日。报工、质量评价、工序交接评价和改进计划状态快照使用同一边界。

## 数据模型

### 规则版本 `performance_rule_versions`

字段至少包括：

- `id`、`version_code`、`name`
- 五维权重和等级阈值
- 交付目标工作日
- 质量扣分、工序交接扣分和改进计划计分参数
- `status`：`draft`、`published`、`retired`
- `effective_from_month`、`effective_to_month`
- `created_by`、`created_at`、`published_by`、`published_at`

首个 V2 规则保留当前权重：产量 35、质量 30、交付 15、纪律 10、改进 10。已发布且被批次引用的规则不可修改或删除；调整规则必须发布新版本。

### 岗位目标版本 `performance_position_target_versions`

字段至少包括：

- `id`、`position_id`
- `target_output_qty`
- `minimum_effective_work_days`
- `effective_from_month`、`effective_to_month`
- `status`：`draft`、`approved`、`retired`
- `created_by`、`created_at`、`approved_by`、`approved_at`

同一岗位的已批准目标版本生效区间不得重叠。岗位目标和最低有效报工日没有系统隐式默认值，必须显式配置和批准。被绩效结果引用后不得修改或删除。

### 绩效批次 `performance_batches`

字段至少包括：

- `id`、`production_month`、`version`
- `period_start`、`period_end`、`source_cutoff_at`
- `rule_version_id`、`input_digest`
- `status`：`draft`、`supervisor_review`、`approval_pending`、`approved`、`superseded`、`cancelled`
- `prepared_by`、`prepared_at`、`submitted_at`
- `approved_by`、`approved_at`
- `supersedes_batch_id`、`superseded_by_batch_id`
- `revision_reason`、`row_version`

约束：

- `(production_month, version)` 唯一。
- 同一生产月份最多一个未被取代的已批准批次。
- `prepared_by` 不得等于 `approved_by`。
- 已批准、已取代或已取消批次不可更新、删除或追加员工修订版。
- 批次状态变更使用 `row_version` 检测并发冲突。

### 员工评分修订版 `performance_score_revisions`

同一批次内，主管每次有效复核都会追加员工修订版，不覆盖上一个修订版。字段至少包括：

- `batch_id`、`user_id`、`revision`
- 员工编号、姓名、部门、岗位和角色快照
- `eligibility_status`：`eligible`、`insufficient_data`
- `eligibility_reason_code`、`eligibility_reason`
- 产量、报工数、有效报工日和质量指标快照
- 五个维度分数、总分、等级、排名和排名样本数
- `rule_version_id`、`position_target_version_id`
- `review_revision_id`、`input_digest`
- `calculated_at`、`created_by`
- 对应 Legacy 结果标识、Legacy 分数和差异摘要

`(batch_id, user_id, revision)` 唯一。当前修订版通过最大修订号确定；批次批准后禁止再追加。合格评分必须绑定规则、岗位目标和输入摘要；数据不足记录可以没有岗位目标，但必须保存明确原因且分数、等级和排名为空。

### 来源事实 `performance_source_facts`

每个批次保存参与计算的不可变事实：

- `batch_id`
- `fact_type`：报工、报废、返工、质检、交接评价、计划状态
- `source_type`、`source_id`
- `canonical_event_id`
- `business_at`
- 员工、订单、产品、工序、岗位和部门等业务快照
- 数量、状态及计算所需值
- `payload_json`、`source_digest`

同一批次内，同一规范事件和指标只能出现一次。事实快照插入后不可更新；源业务后来改变时只能生成新批次版本。

### 质量事件归一化

新增规范质量事件及来源映射，使报废、返工、质检和工序交接记录能够指向稳定的 `quality_event_id`。同一质量问题的多个来源只生成一个绩效事实。历史来源无法可靠合并时进入异常队列，由人工确认合并、确认独立或排除；系统不得按相似文本、数量或时间自动猜测。

### 复核与事件

`performance_reviews_v2` 保存每次主管复核输入及版本，`performance_batch_events` 保存准备、重算、提交、退回、批准和取代事件。两者均为追加式记录。批次退回必须保存原因，主管修改复核后生成新的员工评分修订版。

## 参评资格与评分规则

参评人员范围由生产月内有效的组织与岗位关系，加上该月存在有效绩效来源事实的人员共同确定；不得因为员工当前已离职、停用或调岗而把历史人员排除。缺少可靠历史任职关系时进入岗位归属异常。员工同时满足以下条件才是 `eligible`：

1. 生产月内属于绩效适用人员。
2. 有可确认的岗位快照和当月已批准岗位目标。
3. 有效产量大于零。
4. 有效报工日达到该岗位目标版本配置的最低要求。
5. 不存在未确认的来源重复、岗位归属或其他计算异常。

任一条件不满足时标记为 `insufficient_data`，保存原因，不计算等级和排名，也不触发奖惩。没有质量事件不等于缺少质量数据；存在有效产量且来源完整时，零缺陷按零扣分处理。

首个 V2 版本沿用当前五维业务规则：

```text
产量分 = min(有效产量 / 岗位目标产量, 1) × 35
不良数量 = 去重后的报废数量 + 返工数量 + 质检失败数量
质量基数 = 有效产量 + 不良数量
质量分 = max(0, (1 - 不良数量 / 质量基数) × 30 - 已确认工序交接扣分)
交付分 = min(有效报工日 / 规则目标工作日, 1) × 15
纪律分 = 10 - 已确认纪律扣分
改进分 = 按截止时点的计划状态、复评结果和规则版本计算，上限 10，下限 0
总分   = 五维分数之和，上限 100，下限 0
```

主管评议沿用现有 0 至 10 输入，但只作为相对默认 10 分的扣分，不能给客观指标额外加分。纪律扣分、改进调整或主管评议低于 10 分时必须填写原因。

排名仅包含同一岗位的合格参评员工。同岗位合格样本少于 3 人时不发布排名；并列分数使用并列排名，并以稳定员工主键保证输出顺序确定，但主键不参与名次计算。

## 批次生成与审批流程

1. 制单人选择生产月份和已发布规则版本，系统计算 07:00 统计区间。
2. 采集截止时点内的来源事实，固化人员、组织、岗位和业务快照，生成输入摘要。
3. 绑定每名员工当月生效的岗位目标，判断参评资格并生成首个员工评分修订版。
4. 来源重复、岗位不明或配置缺失进入异常清单。配置缺失可以经确认后作为数据不足原因，但不得生成评分。
5. 批次进入 `supervisor_review`，各部门主管仅能复核本部门员工。
6. 主管保存复核时，在同一事务中追加复核版本、重新计算该员工评分，并重新计算同岗位合格人员的完整排名。被复核员工以及名次发生变化的同岗位人员都追加评分修订版，且使用同一计算时间和排名输入摘要；任一步失败则全部回滚。
7. 制单人执行完整性检查。所有异常必须已解决或被明确确认为数据不足，所有合格评分必须绑定规则、目标和输入摘要。
8. 批次进入 `approval_pending`。批准人只能批准或退回，不能修改评分内容。
9. 批准操作在单一事务中锁定批次、取代原正式版本并使新版本生效。

允许的状态转换：

```text
draft -> supervisor_review -> approval_pending -> approved -> superseded
supervisor_review -> draft
approval_pending -> supervisor_review
draft/supervisor_review -> cancelled
```

退回或取消转换必须填写原因。提交审批前重新计算当前来源摘要；如果相对 `source_cutoff_at` 出现输入变化，则阻止提交，取消旧草稿并创建下一批次版本重新采集。已批准结果如需修正，只能从该版本复制输入并创建下一版本，重新完成全部复核和批准步骤。

## 错误处理与并发

- 采集、复核重算、提交或批准失败时回滚整个事务，不产生半正式结果。
- 所有写命令携带幂等键；相同命令重试返回原结果，不重复创建版本或事件。
- 状态命令携带 `row_version`；版本过期返回 409 `PERFORMANCE_STALE_VERSION`。
- 旧覆盖式写接口返回 409 `LEGACY_LEDGER_READ_ONLY`。
- 规则或岗位目标缺失返回可处理异常 `PERFORMANCE_TARGET_MISSING`，对应员工只能进入数据不足状态。
- 来源关系不明确返回 `PERFORMANCE_SOURCE_AMBIGUOUS`，处理前不能形成合格评分。
- 非法状态转换返回 409 `PERFORMANCE_INVALID_TRANSITION`。
- 制单人与批准人相同返回 403 `PERFORMANCE_SEPARATION_OF_DUTIES`。
- 每次失败和拒绝均写入事件日志，但不记录敏感请求正文。

## 权限与数据范围

新增权限：

- `performance:view_self`
- `performance:view_department`
- `performance:view_all`
- `performance:review_department`
- `performance:prepare`
- `performance:approve`
- `performance:plan_manage`
- `performance:plan_reassess`

部门管理范围使用显式的用户与部门授权关系，不根据角色名称猜测。历史评分按其中的部门快照归属；当前负责该部门且具有部门查看权限的用户可以查看该部门历史结果。

规则：

- 普通员工只能查看本人正式绩效和本人改进计划。
- 部门查看者只能读取其授权部门的记录。
- 全局查看者可以读取全公司记录，但不能因此修改。
- 部门复核者只能修改授权部门内、处于主管复核状态的员工记录。
- 制单人可以准备、计算、处理异常和提交批次，但不能批准自己的批次。
- 批准人必须同时具备全局查看和批准权限。
- 计划负责人不能复评自己的计划。
- 通配管理员权限不能绕过制单人与批准人、计划负责人与复评人的职责分离。

生产主管按负责部门获得查看与复核权限；绩效专员获得全局查看和制单权限；独立批准人获得全局查看和批准权限。质检员和仓库管理员现有的广泛 `performance:view` 不自动映射到全局查看；未显式授权时仅保留本人查看。

数据范围必须在仓储查询和命令入口统一注入。查询参数中的 `user_id`、`department_id` 或批次 ID 不能扩大调用人的授权范围。拒绝的越权请求进入安全审计日志。

## 改进计划状态机

新计划结构包含计划主表、状态事件、证据和复评记录。状态限定为：

```text
draft -> active -> reassessment_pending -> closed
draft -> cancelled
active -> cancelled
reassessment_pending -> active
```

规则：

1. `draft -> active` 前必须填写问题依据、可衡量目标、行动措施、负责人和截止日期。
2. `active -> reassessment_pending` 必须提交至少一项证据，并记录申请复评时间。
3. 独立复评人保存检查时间、引用证据、结论和说明。
4. 复评通过时进入 `closed`；复评不通过时回到 `active`，复评轮次加一，并要求填写新措施和新截止日期。
5. 取消必须填写原因，并由计划管理权限执行。
6. 计划负责人不能担任该计划的复评人。
7. 绩效评分读取生产月截止时点的计划状态和复评事件快照，后续状态变化不改写已批准评分。

旧计划按当前状态迁移。无法映射到合法状态或缺少复评依据的记录进入迁移异常清单，不伪造复评证据。

## 接口设计

现有查询接口保持兼容：

- `GET /api/performance/scores` 返回当前正式版本，并增加版本、来源、状态和生产月区间字段。
- 没有已批准 V2 时返回 Legacy V1，并明确 `result_source=legacy_v1`。
- 原生成和覆盖式复核写接口停止写入旧表，返回只读保护错误，并由新界面改用版本化接口。

新接口按资源和动作划分：

- `GET/POST /api/performance/rule-versions`
- `GET/POST /api/performance/position-target-versions`
- `GET/POST /api/performance/batches`
- `POST /api/performance/batches/{id}/prepare`
- `POST /api/performance/batches/{id}/submit-supervisor-review`
- `POST /api/performance/batches/{id}/members/{user_id}/reviews`
- `POST /api/performance/batches/{id}/submit-approval`
- `POST /api/performance/batches/{id}/approve`
- `POST /api/performance/batches/{id}/return`
- `GET /api/performance/batches/{id}/exceptions`
- `GET /api/performance/batches/{id}/comparison`
- `POST /api/performance/plans/{id}/transitions`
- `POST /api/performance/plans/{id}/evidence`
- `POST /api/performance/plans/{id}/reassessments`

所有列表接口在分页前应用数据范围。所有命令接口返回新状态、`row_version` 和事件标识，方便前端处理并发冲突和幂等重试。

## 界面设计

绩效页面提供以下视图：

- 正式结果：显示生效版本、07:00 统计区间、参评状态、五维分数和排名。
- 版本对比：逐人展示 Legacy V1、V2 或后续版本差异及原因。
- 批次审批：面向制单人和批准人显示状态、完整性检查、退回原因和审批事件。
- 数据异常：处理岗位缺失、目标缺失和质量来源不明确问题。
- 岗位目标：维护草稿、生效区间和批准记录。
- 改进计划：展示执行状态、证据、复评轮次和结论。

“数据不足”使用独立状态展示，不显示红、黄、绿等级，也不显示名次。旧版本明确标注 Legacy，已取代版本只读。前端根据权限控制可见动作，但不承担最终授权判断。

## 历史迁移

迁移采用只增不改策略，从数据库版本 55 的生产副本开始验证：

1. 备份生产数据库和应用版本，记录基线校验和。
2. 创建新台账、规则、目标、来源、事件、权限和改进计划表及数据库约束。
3. 将现有 `performance_scores` 和 `performance_reviews` 登记为 Legacy V1，只读保留原主键、当前值和时间信息。
4. 对 64 条曾被覆盖的评分标记 `prior_revisions_unavailable`。没有可靠备份时不尝试恢复早期修订。
5. 对缺少稳定岗位快照的 30 条记录建立人工确认清单。可靠岗位历史可以映射；其余标记岗位依据不足，不使用当前岗位自动回填。
6. 按生产月份配置并批准历史岗位目标、最低有效报工日和 V2 规则。
7. 使用 07:00 口径生成影子 V2。已知 5 条报工和 11 条质量评价的月份变化必须在逐条差异报告中可解释。
8. 对重复质量来源、岗位归属和其他异常逐条确认；未确认记录不得形成合格评分。
9. 生成 Legacy V1 与 V2 逐人对账，差异分类为月份边界、岗位目标、质量去重、参评资格、主管复核或规则变化。
10. 完成迁移验收后提交首个 V2 批次审批。

历史月份都可以生成 V2；缺少可靠岗位或目标的员工按已确认规则记为数据不足，不猜测评分。某月 V2 未批准前，该月继续以 Legacy V1 作为正式查询结果。

## 发布与回滚

1. 在生产数据库副本上完成迁移、重算、权限和性能验证。
2. 部署只增式数据库迁移及新后端，默认关闭普通用户 V2 查询切换。
3. 启用管理员影子计算、异常处理和 V1/V2 对账。
4. 完成首个批次双人审批后，将正式查询切换到 V2。
5. 连续两个完整生产月核对评分、权限拒绝、异常处理和计算耗时，期间不写入工资台账。
6. 观察期结束后单独评审工资联动，不在本次发布中自动启用。

应用回滚只切回 Legacy 查询入口和上一应用版本；已写入的 V2 表与事件完整保留，不执行反向删表或覆盖 Legacy 数据。数据库层的 Legacy 只读触发器在回滚期间继续生效，使旧生成和复核写接口失败关闭，不能恢复覆盖式写入。重新上线时从现有 V2 状态继续，避免重复迁移。

## 测试策略

### 评分单元测试

- 零产量、负数或无效产量不能产生等级。
- 缺少岗位、岗位目标或最低有效报工日时进入数据不足。
- 岗位目标变更不改变已批准版本。
- 五维权重、上限、下限和主管只扣分规则正确。
- 同岗位少于 3 名合格员工时不发布排名。

### 时间与来源测试

- 月初 06:59:59 归上月，07:00:00 归本月。
- 统计范围使用左闭右开边界，不重复或遗漏临界记录。
- 报工、质量评价、交接评价和计划状态使用同一生产月。
- 同一规范质量事件的多个来源只计一次。
- 来源不明确时阻断合格评分并形成异常。

### 事务与数据库约束测试

- 复核保存失败时，复核版本和评分修订版均不落库。
- 评分重算失败时，复核输入也不落库。
- 一名员工分数变化时，同岗位受影响人员的排名修订在同一事务完成，不出现混合计算时间排名。
- 并发修改返回 409，不静默覆盖。
- 制单人不能批准自己的批次。
- 已批准和已取代版本不能更新、删除或追加修订版。
- 非法改进计划状态转换被拒绝。

### 权限测试

- 本人查看不能读取其他员工。
- 部门查看只能覆盖显式授权部门，包括按部门快照归属的历史结果。
- 全局查看不自动获得准备或批准权限。
- 修改查询参数、对象 ID 或分页条件不能扩大数据范围。
- 质检员和仓库管理员不会因旧权限迁移获得全局绩效访问。
- 计划负责人不能复评自己的计划。

### 迁移、接口与前端测试

- 在生产数据库副本上验证 Legacy 导入数量、V2 生成数量和差异分类。
- 验证 64 条不可恢复修订和 30 条岗位快照异常均有明确标识。
- 验证已知 5 条报工和 11 条质量评价的月份变化。
- 验证准备、复核、提交、退回、批准、取代和 Legacy 回退完整流程。
- 验证正式结果、版本对比、异常、岗位目标和改进计划界面。
- 保持原后端 51 项绩效定向测试、前端 57 项单元测试通过，并执行后端和前端完整回归测试。

## 验收标准

1. 零产量和数据不足员工的正式结果中，分数、等级和排名均为空。
2. 每条合格正式评分均绑定规则版本、岗位目标版本、来源输入摘要和主管复核版本。
3. 已批准批次可从来源快照重复计算出相同结果和输入摘要。
4. 同一规范质量事件在同一批次中的计分次数为 1。
5. 提交审批时未确认异常数量为 0。
6. 同岗位少于 3 名合格员工时不发布排名。
7. 本人、部门和全局权限矩阵全部通过，跨范围数据泄露为 0。
8. 制单人与批准人、计划负责人与复评人的职责分离不可绕过。
9. 已批准版本不能原地改变，V3 修订能够保留并取代 V2。
10. Legacy V1 与 V2 差异能够逐人解释，已知跨月记录能够逐条追溯。
11. 连续两个完整生产月内，绩效模块写入工资台账的记录数为 0。
12. 部署后服务健康检查、关键接口、前端页面和完整回归测试通过。

## 实施分期

### 第一阶段：数据与安全基础

新增规则、岗位目标、批次、修订、来源和事件表；实现 07:00 边界、不可变约束、权限目录和数据范围服务；冻结 Legacy 写入。

### 第二阶段：评分与审批闭环

实现事实采集、纯评分引擎、主管复核原子事务、批次状态机、双人批准、质量来源去重和并发控制。

### 第三阶段：改进计划与界面

实现计划状态机、证据和复评；完成正式结果、版本对比、审批、异常和岗位目标界面。

### 第四阶段：历史迁移与生产发布

在生产副本完成 Legacy 导入和影子 V2，对异常进行人工确认，完成双人审批后切换正式查询，并进入两个完整生产月的无工资联动观察期。
