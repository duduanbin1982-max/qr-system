# 物料审计修复设计

基线：`8110dddc9b5ff7b9835bd9561c749cb4d2a136dc`。
范围：物料管理审计 C1–C3、W1–W8；仅本地实现和验收，不操作生产、不自动修历史数据。

## 已确认的业务规则

- `process_id IS NULL` 为订单通用用料，按订单扣一次。
- 首笔获批正常报工触发通用用料，数量为订单数量 × 冻结单位用量；工序专用料仍按本次报工数量。
- 禁止将“零行快照”直接解释为“无快照”，禁止静默读取实时产品 BOM。

## 快照与历史兼容策略

1. 建单在原事务内写快照初始化不可变事件，包括无产品、空 BOM 的明确空快照。
2. 旧订单非空订单配方可作为已存在快照使用；零行且无初始化事件时返回 `MATERIAL_SNAPSHOT_UNKNOWN`，等待单独审核的来源确认。
3. 初次通用扣料冻结完整通用配方、订单数量、digest 和消费/原日志 ID，空通用配方也保存依据。
4. 旧订单已有报工或自动消耗、无法证明通用料未扣时返回 `LEGACY_AMBIGUOUS`，不自动补扣或猜测历史。
5. 通用料消费的工序及报工来源均为空，其领域来源是订单；日志使用 `order_common_consumption`，冻结事件记录触发报工。专用料保留现有报工外键。两者同料时分记录、先合并验库存。
6. 后续核验全订单冻结依据及原消费/日志，包含已撤销或当前配方已删除的材料。修改数量/通用配方、撤销后再次报工均显式冲突，不隐式重扣或退料。
7. 事件读取覆盖当前及归档审计，核验事件类型、目标、版本、payload、digest 和跨表矛盾。初始化事实与扣料冻结依据分别负责来源和耗料基线，不用初始化 digest 禁止合法的扣前配方编辑。
8. 全部写入加入报工已有短写事务；无内部 commit、无新 schema。订单级幂等依赖受控入口和现有 `BEGIN IMMEDIATE` 串行化，不声称原报工唯一索引能保证订单级唯一。

上述兼容策略经独立消费链设计评审后实施。历史未知/歧义订单的生产基线确认与修复另行审核授权，本轮不自动执行。

## 其他修复

- 库存、流水或业务引用存在时禁止物理删除；预检和事务内重检共用规则。
- 共用有限数值策略，拒绝布尔值、非法类型、NaN、无穷和溢出；校验输入和计算结果。
- 手工领料必需审计与库存、消费、日志同事务；撤销保留完整原日志关联。
- 名称创建与更新都去空白并验证，保留现有名称唯一语义。
- 前端订单搜索变动撤销旧选择，异步操作绑定弹窗会话和实体。
- 有效消耗排除已撤销记录并显示状态；配方选料完整分页加载。

## 验收

定向后端及前端回归、真实报工事务与失败回滚、归档后幂等、数值和配方边界、弹窗异步行为、分页、全量后端/前端单测、架构与 API facade、构建和 E2E。
最后对完整 diff 独立复审，排除历史文件、临时报告、数据库及依赖目录。提交和生产发布需后续授权。
