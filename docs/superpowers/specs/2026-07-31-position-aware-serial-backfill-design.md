# 跨工序补报按活动岗位匹配设计

## 状态

- 设计日期：2026-07-31
- 状态：已确认
- 适用范围：移动端序列号跨工序补报、补报审批与追溯

## 背景

当前正常报工已按登录会话中的活动岗位筛选工序，但序列号跨工序补报只校验操作员个人工序授权。多岗位人员因此可能看到或提交不属于当前活动岗位的补报工序，页面展示与岗位责任边界不一致。

本设计让跨工序补报以当前活动岗位为第一匹配条件，由后端统一计算候选并在提交时再次校验。操作员不再填写实际完成时间和补报原因，系统自动记录申请时间和岗位快照。

## 目标

1. 补报候选严格限制为当前活动岗位所关联的工序。
2. 唯一候选自动选中；多个候选必须由操作员明确选择。
3. 当前岗位无候选时不回退到其他岗位或个人补充授权。
4. 后端强制执行岗位边界，旧页面或直接请求无法绕过。
5. 补报申请自动记录提交岗位，审批和追溯可以还原责任上下文。
6. 去除实际完成时间和补报原因的人工填写与必填校验。

## 非目标

- 不改变正常报工的岗位与工序选择规则。
- 不删除历史补报记录或历史字段。
- 不自动提交补报申请。
- 不允许系统在没有明确活动岗位时猜测岗位。

## 核心规则

后端按以下交集计算当前岗位可补报候选：

```text
个人授权工序
∩ 当前活动岗位关联工序
∩ 当前订单工艺路线
∩ 尚未报工且允许补报的工序
= 当前岗位可补报候选
```

候选数量决定交互：

| 候选数 | 行为 |
| ---: | --- |
| 0 | 禁止补报，提示切换岗位，不回退其他岗位 |
| 1 | 自动选中候选，切换手动模式并展开补报确认 |
| 2个及以上 | 不默认选择，按工艺顺序列出当前岗位候选 |

补报始终由操作员点击提交，不因唯一候选而自动提交。

## 后端设计

### 扫码候选计算

`MobileScanService` 继续通过 `ActivePositionService` 获取当前会话的活动岗位及其 `process_ids`。`ProcessOrderService` 在现有个人授权、序列号状态、订单进度和补报开关基础上，增加活动岗位范围校验。

每道工序的 `serial_backfill_reportable` 只有在以下条件全部满足时为 `true`：

- 当前为序列号模式；
- 系统已开启受控补报；
- 操作员拥有补报权限；
- 工序在个人授权范围内；
- 工序在当前活动岗位的工序范围内；
- 工序属于当前订单工艺路线；
- 工序不是工件当前工序；
- 该序列号在该工序未报工且无待审批申请；
- 工序未整体完成且仍有可报数量。

订单扫码响应新增：

- `serial_backfill_selection_source`：`position_auto`、`position_manual` 或 `none`；
- `serial_backfill_candidate_count`：当前岗位候选数；
- `serial_backfill_message`：给移动端直接展示的明确提示。

### 提交校验

提交补报时，后端重新读取当前登录会话的活动岗位，不信任前端传入的岗位范围。目标工序必须同时属于个人授权和当前活动岗位。

如果扫码后活动岗位发生变化，或者提交的工序不再属于当前活动岗位，提交失败并要求重新确认。前端不传岗位名称作为可信数据，岗位快照由后端根据活动岗位生成。

### 去除人工补充字段

新补报请求不再要求：

- `actual_completed_at`
- `backfill_reason`

领域命令和补报服务不再对这两个字段执行必填校验。数据库现有字段保留，以兼容历史记录；新记录可以为空。申请时间使用系统生成的 `created_at`，并在界面上明确称为“申请时间”，不冒充实际完成时间。

## 移动端设计

订单确认页显示当前活动岗位。操作员存在多个岗位时提供“切换岗位”入口；切换成功后使用原扫码内容重新请求订单和补报候选，无需再次扫码。

### 唯一候选

- 自动选中候选工序；
- 自动切换到手动模式；
- 滚动并高亮所选工序；
- 显示提交按钮；
- 不显示实际完成时间和补报原因；
- 不自动提交。

### 多个候选

- 显示完整工艺路线；
- 只有当前岗位候选可点击；
- 不默认选中；
- 提示“当前岗位有多个可补报工序，请选择本次实际完成的工序”。

### 无候选

- 禁用提交按钮；
- 提示“当前岗位‘岗位名称’没有可补报工序，请切换岗位”；
- 不把其他岗位或个人补充授权工序显示为可补报。

提交确认内容包含订单、序列号、当前岗位和目标工序。

## 数据模型与迁移

在 `work_records` 增加岗位快照字段：

- `submit_position_id`：提交时活动岗位ID，可空以兼容历史记录；
- `submit_position_name`：提交时活动岗位名称，可空以兼容历史记录。

创建补报申请时由后端写入快照。岗位配置后续发生变化时，不更新历史快照。

现有 `actual_completed_at` 和 `backfill_reason` 字段不删除、不改写历史数据。审批接口对历史值保持兼容，新记录为空时不显示对应信息。

## 审批与追溯

审批页面的新补报记录显示：

- 订单号；
- 序列号；
- 补报工序；
- 操作员编号和姓名；
- 提交岗位；
- 申请时间；
- 审批状态和审批人。

历史记录已有实际完成时间或补报原因时可以只读显示。新记录不显示空的历史字段。

## 错误处理

| 场景 | 提示 |
| --- | --- |
| 未选择活动岗位 | 请先选择当前岗位 |
| 当前岗位无候选 | 当前岗位“岗位名称”没有可补报工序，请切换岗位 |
| 多候选未选择 | 当前岗位有多个可补报工序，请选择本次工序 |
| 工序不属于当前岗位 | 所选工序不属于当前岗位，请重新选择 |
| 扫码后岗位变化 | 当前岗位已变化，请重新确认补报工序 |
| 已报工 | 该工序已报工，不能重复提交 |
| 已有待审批申请 | 该工序已有待审批补报申请 |

## 安全与一致性

- 候选计算和提交校验使用同一岗位范围规则。
- 提交权限、个人工序授权和岗位工序范围全部由后端校验。
- 前端过滤只负责交互，不作为安全边界。
- 岗位快照取自服务端会话上下文，不能由请求覆盖。
- 审批通过前仍不推进序列号当前工序状态。

## 测试与验收

必须覆盖：

1. 单岗位单候选自动选中，但不自动提交。
2. 单岗位多候选必须选择。
3. 多岗位人员只看到当前活动岗位候选。
4. 当前岗位无候选时不回退其他岗位。
5. 切换岗位后使用原扫码内容重新计算候选。
6. 未设置活动岗位时拒绝补报。
7. 直接构造请求不能提交其他岗位工序。
8. 扫码后切换岗位，旧候选提交被拒绝。
9. 新补报不需要实际完成时间和原因。
10. 补报记录保存提交岗位快照。
11. 审批页面显示岗位快照和申请时间。
12. 已报工或待审批工序不能重复申请。
13. 历史补报记录仍可查看原时间和原因。
14. 正常报工流程无回归。
15. 使用操作员0703和序列号26062502-022进行真实移动端回归。

## 发布与回滚

先执行可向后兼容的数据库迁移，再部署后端候选与校验逻辑，最后部署移动端和审批页面。静态资源需要提升版本号和Service Worker缓存版本。

发布后验证单候选、多候选、无候选和切换岗位四种状态。回滚应用代码时保留新增的可空快照字段，不需要回退数据库结构。
